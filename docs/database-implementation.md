# Database Implementation Notes

## Local Setup

Install Python dependencies:

```powershell
python -m pip install -e ".[test]"
```

Start local PostgreSQL 16:

```powershell
docker compose up -d postgres
```

Create the test database once:

```powershell
docker compose exec postgres createdb -U bellum_resources bellum_resources_test
```

Set environment variables:

```powershell
$env:BELLUM_DATABASE_URL = "postgresql+psycopg://bellum_resources:change_me@localhost:5432/bellum_resources"
$env:TEST_DATABASE_URL = "postgresql+psycopg://bellum_resources:change_me@localhost:5432/bellum_resources_test"
```

Run migrations:

```powershell
python -m alembic upgrade head
```

Normal Alembic commands resolve their database from `BELLUM_DATABASE_URL`. Test runs do not rely on
environment-variable precedence for migrations; the pytest Alembic fixture sets `sqlalchemy.url` directly
from `TEST_DATABASE_URL`, and the migration environment honors that explicit config value first.

Downgrade:

```powershell
python -m alembic downgrade base
```

Run tests:

```powershell
python -m pytest
```

## Seed Strategy

The first migration seeds immutable/required reference data needed for a usable empty database:

- source systems: `galaxy_harvester`, `core3`
- source instances: `galaxy-153`, `bellum-gero-live`
- server instance: `bellum-gero-live`
- ten known planets
- stat definitions: `CR`, `CD`, `DR`, `FL`, `HR`, `MA`, `PE`, `OQ`, `SR`, `UT`, `ER`

No resources, unresolved GH names, schematics, creatures, loot, items, or Core3 live data are seeded.

Required reference rows live in the migration so an empty PostgreSQL database can be upgraded reproducibly without a separate manual seed step. Future large/imported datasets should use explicit importer commands, not migrations.

## Primary Keys and Public IDs

Internal relational tables use PostgreSQL generated `BIGINT IDENTITY` primary keys. This keeps high-volume observation, source identity, stat, snapshot, and history tables compact and efficient.

Canonical resources use:

- `resources.id`: internal `BIGINT IDENTITY` primary key
- `resources.public_id`: stable public UUID generated by PostgreSQL `gen_random_uuid()`

The public UUID is the future API/URL-safe identity. Internal bigint IDs should not be treated as permanent public identifiers.

## NULL Epoch Uniqueness

`source_resources` uses PostgreSQL 16 `UNIQUE NULLS NOT DISTINCT`:

```sql
UNIQUE NULLS NOT DISTINCT (source_instance_id, server_epoch_id, source_resource_id)
```

This prevents duplicate source identities even when `server_epoch_id` is `NULL`, which is required for Galaxy Harvester identities. GH is not assigned a fake Core3 epoch.

## JSONB Boundary

JSONB columns are limited to supplemental provenance, diagnostics, importer parameters, summaries, and evidence payloads.

Queryable facts remain normalized:

- source identity
- resource names
- resource types
- stats
- planets
- availability
- lifecycle evidence
- timestamps
- source/import identity

JSONB must not become a hidden second resource database.

## Enum-Like Values

This phase uses CHECK constraints only where values affect core data correctness, such as stat presence/value consistency and resource type range applicability.

Status-like fields (`status`, `confidence`, `parse_status`, `mapping_status`, `event_type`, and similar) are text for now. They are expected to evolve as importers and review workflows are implemented. Rigid PostgreSQL enums are deferred until the value sets stabilize.

## Deletion Policy

Foreign keys use PostgreSQL's default `NO ACTION` behavior. Cascading deletes are intentionally avoided for provenance/history tables so historical evidence is not removed accidentally by deleting an application-level row.

Operational cleanup, if ever needed, should be explicit and audited.

## Index Decisions

Implemented now:

- source identity uniqueness with nullable epoch correctness
- source resource lower-case name lookup expression index
- `resource_names(normalized_name)`
- `resource_type_closure(ancestor_type_id, descendant_type_id)` primary key
- `resource_type_closure(descendant_type_id, ancestor_type_id)`
- `resource_planet_observations(planet_id, state, observed_at)`
- `resource_planet_observations(source_resource_id, planet_id, observed_at)`
- `resource_stat_observations(stat_code, value)`
- `resource_match_candidates(status, score)`
- one-confirmed-source partial unique index for identity links

`pg_trgm` is deferred until the search/API phase. The initial database foundation does not yet need fuzzy public search, and delaying it keeps this migration focused on correctness.

## Range and Stat Semantics

`resource_stat_observations` enforces:

- `is_present = true` requires `value IS NOT NULL`
- `is_present = false` requires `value IS NULL`

There is no global `1..1000` stat value constraint. Source anomalies must be preservable.

`resource_type_stat_ranges` enforces:

- exactly one owner: canonical type or source type
- not-applicable ranges have null min/max
- applicable ranges may be unknown, or have `min_value <= max_value`

Importer logic will later decide how to interpret GH `0/0` ranges.
